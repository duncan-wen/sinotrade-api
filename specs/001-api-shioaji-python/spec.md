## 使用者情境與測試 *(強制性)*

### 主要使用者故事
- **(Viewer)** 作為一個 `viewer`，我希望能請求商品即時市場數據，以便我能觀察市場動態。
- **(Trader)** 作為一個 `trader`，我希望能請求即時數據並執行模擬下單，以便我能測試交易策略。

### 驗收情境
1. **假設** 我有一個有效的 API 金鑰和一個有效的金融商品代碼 (如股票 '2330' 或選擇權 'TXO202509W1C17000')，**當** 我請求該商品的報價時，**那麼** 系統會回傳最新的買入價、賣出價和成交量。
2. **假設** 我有一個有效的 API 金鑰但一個無效或不存在的商品代碼，**當** 我請求報價時，**那麼** 系統會回傳一個錯誤訊息，指出找不到該商品。
3. **假設** 我有一個無效的 API 金鑰，**當** 我請求報價時，**那麼** 系統會回傳一個驗證錯誤。

### 邊界案例
- 當與上游的 Shioaji API 連線中斷或回傳錯誤時會發生什麼？
- 系統如何處理來自單一使用者對同一商品的大量請求？為兼顧效能與資料即時性，將實作1秒過期的快取機制。
- 報價請求的預期回應時間是多少？系統的回應時間將取決於上游 Shioaji API 的效能。我們的目標是將自身的處理延遲降至最低 (例如，少於 50 毫秒)。

## 需求 *(強制性)*

### 功能需求
- **FR-001**：系統必須提供一個安全的 API 端點，用於請求金融商品 (含股票、期貨、選擇權) 的即時報價，此功能對 `viewer` 和 `trader` 角色開放。
- **FR-002**：系統必須在提供 API 存取權限之前對使用者進行身份驗證和授權。初期版本將使用 API 金鑰進行驗證，未來版本計畫升級至 JWT。
- **FR-003**：API 必須允許使用者指定他們想要報價的商品代碼 (例如，股票: '2330', 期貨: 'TXF202310', 選擇權: 'TXO202509W1C17000')。
- **FR-004**：成功報價請求的 API 回應必須至少包含以下欄位：買入價、賣出價、買入量、賣出量、最後成交價和時間戳。
- **FR-005**：對於無效請求、驗證失敗或上游 API 問題，系統必須提供清晰的錯誤訊息。
- **FR-006**：系統必須從永豐金 Shioaji Python 函式庫擷取即時資料。
- **FR-007**：系統必須實作快取機制，其生命週期 (TTL) 為1秒，以平衡效能與資料的即時性。
- **FR-008**：系統必須為 `trader` 角色提供一個 API 端點，用於對任何可交易的金融商品執行模擬下單。

### 非功能需求
- **NFR-001**：系統自身的處理延遲 (不含等待上游 Shioaji API 的時間) 應低於 50 毫秒。

### 關鍵實體 *(如果功能涉及資料則包含)*
- **金融商品 (FinancialInstrument)**：代表一種可交易的金融工具，如股票、期貨或選擇權。
  - **屬性**：商品代碼 (唯一識別碼)、商品類型 (股票/期貨/選擇權)、[其他相關屬性，如到期日、履約價等]。
- **報價 (Quote)**：代表特定時刻商品的即時價格和成交量資訊。
  - **屬性**：商品代碼、買入價、賣出價、買入量、賣出量、最後成交價、時間戳。
- **API使用者 (APIUser)**：代表有權存取交易 API 的使用者。
  - **屬性**：使用者 ID、API 金鑰、角色。定義了兩種角色：`viewer` (僅能讀取報價資料) 和 `trader` (可讀取報價並執行模擬下單)。
- **模擬訂單 (SimulatedOrder)**：代表一個由 `trader` 執行的模擬交易指令。
    - **屬性**：訂單 ID、商品代碼、買賣方向、價格、數量、訂單狀態。
